## 0. 摘要

**"俯视图转速和视频转速不一致"不是一个 bug，是三层叠加的独立问题；你三天加的补丁全部落在第二层，而第一层（过程噪声量级）从第一天起就没动过。**

| 层 | 病灶 | 现状数值 | 后果 |
|---|---|---|---|
| **① 数值层** | 角加速度过程噪声比物理小两个数量级 | `angular_accel = 0.01` → 角加速度容限 **0.1 rad/s²**；参考实现 13~20 rad/s² | 滤波器认为"转速不可能变"，角度残差几乎拉不动 ω |
| **② 架构层** | 为了补偿①，外挂了 17 个 ω 写入点 / 11 个开关 | `updateRate`/`updateYawRate`/`setRate`/`injectRateObservation`/PLL/tracklet/… | 通道之间互相否决，谁赢取决于门限细节，不取决于物理 |
| **③ 观测层** | 量测建在 3D 位姿上，斜板 yaw 病态 → 被硬门拒收 | 每象限可信弧 55~63°/90° → ω 系统性低估 **35%** | 无论① ②怎么调，输入里就没有完整转速信息 |

**一句话**：`0.1 rad/s²` 的角加速度容限意味着"从静止加速到 4.7 rad/s 需要 47 秒"；实车 0.5 秒就能做到。滤波器先验与物理差了约 100 倍，然后你用 17 个补丁去手动喂它转速——这是补丁无效的结构性原因，不是参数没调对。

**根治方向（单一主线，§6）**：把 ω 交还给滤波器（Q 提到物理量级 + P0 对齐），把"喂 ω"的通道全删掉，把观测从"3D 位姿"抬到"角度直接量测 / 像素域"，用 R 自适应降权替代硬门限。这条路线在 `sp_vision_25`、`rmcs_auto_aim_v2`、`awakening` 三个项目里是**同一种写法**，且都没有任何一条 ω 专用通道。

## 1. 先别再改代码：三分钟判别病灶在哪一层

你现在最需要的是**区分**，不是再调一个参数。下面三个判据互斥，跑一次就能定位。

### 判据 A：比值恒定吗？

在俯视图 HUD 读 `omega`，同时用图像域真值（项目已有 `tests/tools/gt_omega.py`）算同一段的真实转速，取 5~10 个点求 `ω_ekf / ω_true`：

| 观测结果 | 结论 | 去修哪里 |
|---|---|---|
| 比值稳定在 **0.45~0.55** 或 **2.0~2.2**（恒定、不随速度变） | 时间基/播放速度问题，不是估计问题 | §6 阶段 0 |
| 比值稳定在 **0.6~0.7** | 观测覆盖截断（文档已实测 62~70%） | §6 阶段 3 |
| 比值**随转速升高而变小**，低速段接近 1 | 过程噪声太小，跟不上加速 | §6 阶段 2（核心） |
| 比值**正负跳变** / 单帧冲 ±10 rad/s | 多通道打架 | §6 阶段 2 |
| 比值≈1 但**画面看着不对** | 纯显示层（坐标/镜像/画法） | §6 阶段 4 |

> 时间基已核对：素材 `data/replay/v4.avi` 实测 `avg_frame_rate=166/1`，`test_camera_playback.cpp:1231` 用 `time_s = frame_index / fps`，与视频一致；`TopDownView.cpp:398` 的 `dt=1/166` 只是观测估计器的兜底默认值。**所以除非你用外部播放器对照，时间基大概率不是主因**——但仍建议先做这条排除，成本 2 分钟。

### 判据 B：方向反了还是慢？

`TopDownView.hpp:16-18` 的坐标约定是"画布上=+x(前)，画布左=+y(左)"，因此车体在图上**逆时针**。而相机在车的对面，视频里看到的是**顺时针**。

**这两者本来就相反。** 如果你是把"视频画面的转向"和"俯视图的转向"直接对照，方向不一致是设计使然，不是 bug。判据：若 `|ω_ekf| ≈ |ω_true|` 但符号相反 → 显示约定问题，不是估计问题。

### 判据 C：蓝板和绿板谁不对？

俯视图上有两套车体：
- **蓝四板** = EKF 状态（`TopDownView.cpp:302`，`phase = state(6) + k·π/2`）
- **绿色实测板/绿圆** = 检测反推（`drawDetectedBody`）

盯黄描边那块板（`aim_slot`）。如果绿板转得对、蓝板跟不上 → 估计层；如果两者一起慢 → 时间基或显示层；如果蓝板"转一下跳一格" → 槽位重绑（§4.4）。

## 3. 参考实现到底怎么让转速跟上的

### 3.1 sp_vision_25：ω 从来不是"被估计"的，是"被捎带"的

```cpp
// tasks/auto_aim/target.cpp:96-121  Piecewise White Noise
v1 = 100;  // 加速度方差
v2 = 400;  // 角加速度方差   ← 关键
Q(6,6)=a*v2; Q(6,7)=b*v2; Q(7,6)=b*v2; Q(7,7)=c*v2;   // a=dt⁴/4, b=dt³/2, c=dt²
```

- `Q(6,7)` 不为零 → 每次 predict 都把 `P(a,w)` 交叉协方差撑大
- 角度残差 `z[3] - h(x)[3]` 经 `K` 流进 `a`，同时经 `P(a,w)` 流进 `w`
- **每一帧都在隐式测速**，不需要任何"转速估计器"

配套三件事（缺一不可）：

| 机制 | 位置 | 作用 |
|---|---|---|
| 角度作为第 4 维直接量测 | `target.cpp:196-222` | 每帧都有朝向观测，不管板多斜 |
| R 随斜视角/距离自适应降权 | `target.cpp:190-196` | `R_angle = log(|Δangle|+1)+1`，越斜越不信但**永不丢** |
| 槽位匹配（角度+方位双判据） | `target.cpp:138-169` | 先定 id 再 update，换板不打架 |
| NIS 滑窗 + lost 重收敛 | `tools/extended_kalman_filter.cpp:74-81` | 大 Q 的兜底，防止乱飘 |

> 注意：`target.cpp:241-250 diverged()` 用半径越界做整体作废；`tracker.cpp:243-262` 里 `P0(w)=100`（σ=10 rad/s）——**初始就承认"我完全不知道转速"**。

### 3.2 rmcs_auto_aim_v2：把量测搬到像素域，从根上消灭 PnP 病态

```cpp
// src/module/tracker/model/robot.cpp:444  update(const Vector2d& upper, const Vector2d& lower, int id)
// 量测 = 一条灯条的上下两个端点像素，4 维
// H = 4×11，链式：状态 → 8 条灯条 3D 端点 → 相机 → 像素
```

状态与噪声（`robot.cpp:55-100`）：

```cpp
// [x, vx, y, vy, z, vz, a, w, rf, rl, hl]
P0 = diag(64,64,64,  64,64,64,  0.4, 100,  1e-2,1e-2,1e-2)
Q  = diag(1e-4,1e-4,1e-8,  2e-1,2e-1,1e-8,  1e-3, 1.0,  1e-8,1e-8,1e-8)
R  = diag(40,40,40,40)   // 像素²
```

**最值得抄的是它的可见性模型**（`robot.cpp:170-200`）：

```
板面与视线夹角 < 70°  → 两条灯条都可见（8 维→4 维/条）
70° ~ 90°            → 只有朝相机那条灯条可见（仍有 4 维像素）
> 90°                → 不可见，跳过
```

这意味着：**斜板不是"被拒收"，而是"少用一半信息"**。而你现在是斜板 → yaw 不可信 → 硬门拒收 → 覆盖缺口 35%。

### 3.3 awakening：3D 姿态 + 投票器消歧

// motion_model.hpp:21
enum { CX, VCX, CY, VCY, CZ, VCZ, C_ROT_Z, VYAW, LOG_R1, P1, P2, C_ROT_Y, C_ROT_X, X_N };

## 4. 逐项差距（带 file:line）

### 4.1 数值层：角加速度容限差 100 倍（**这是主因**）

`student/include/RotatingArmorModel.hpp:53`

```cpp
double angular_accel{0.01}; // (rad/s^2)^2 / Hz
```

`student/src/RotatingArmorModel.cpp` 的 `addWhiteAccelerationNoise` 实现 `q·[[dt³/3, dt²/2],[dt²/2, dt]]`，所以在 166 fps 下：

```
Q(w,w) = 0.01 × dt = 0.01 / 166 = 6.0e-5      → 每帧 σ_ω = 0.0078 rad/s
```

折算成"角加速度容限"：`σ_a = √q = 0.1 rad/s²`。

**物理对照**：RM 旋转车体从 0 加速到 4.7 rad/s 大约 0.3~0.5 s → 真实角加速度 **10~15 rad/s²**。你的滤波器认为转速只能以 0.1 rad/s² 变化，即**需要 47 秒**才能到 4.7 rad/s。差约 100~150 倍。

同一个量在参考实现里：

| | Q(ω,w) 每帧 | σ_ω/帧 | 折算角加速度容限 |
|---|---|---|---|
| 你的项目 | 6.0e-5 | 0.0078 | **0.1 rad/s²** |
| sp_vision_25 (`v2=400`) | 0.0145 | 0.12 | **20 rad/s²** |
| rmcs (`noise_rotation_speed=1.0`) | 1.0 | 1.0 | **12.9 rad/s²**（按 √(q/dt) 折算） |

> `RotatingArmorModel.hpp:54-57` 的注释写着"直接对齐 v2=400 会破坏合成收敛契约 dyaw=0.58/d_omega=-3.08"。**这句注释正是问题的化石**：它说明有人试过、被测试挡住了，然后退回 0.01，改用外部通道硬灌。测试保护了一个错误的取舍——详见 §5。

### 4.2 架构层：17 个 ω 写入点

```bash
$ grep -c 各写入 API student/src/RotatingArmorTracker.cpp
updateRate(                    2   # EKF 第5维量测
updateYawRate(                 3   # 法向斜率窗口
setRate(                       6   # 硬写状态，绕过协方差
injectRateObservation(         1   # 外部注入（还先膨胀 P(7,7)）
updateYawRateFromWindow(       2   # 0.35s 窗口最小二乘
forced_omega                   3   # 配置强制
```

对应 11 个 `rate_*` 开关：`rate_update_enabled`、`rate_from_chord_enabled`、`rate_from_raw_normal_enabled`、`rate_from_residual_enabled`、`rate_from_tracklet_enabled`、`tracklet_rate_enabled`、`tangent_rate_enabled`、`rate_window_enabled`、`rate_measurement_enabled`…

**同一个物理量被 17 个来源写、11 个开关控制**，任何单点改动都会被其它通道的否决逻辑吃掉。这不是"参数没调好"，是**结构上不可调**。

顺带一个"补丁残骸"的铁证（`RotatingArmorTracker.cpp:2996-2999`）：

```cpp
const bool spinning =
    spin_streak_ >= config_.rate_tracklet_min_streak &&
    std::fabs(rate_signed_ema_) >= config_.rate_tracklet_min_rate_rad_s;
    std::fabs(ekf_.state()(7)) >= config_.rate_tracklet_min_rate_rad_s;   // ← 死语句
```

最后一行是被删掉的 `||` 分支留下的空表达式语句。它不改变行为，但**证明改动是盲改的**——没人编译后看警告。

### 4.3 观测层：量测建在 3D 位姿上，斜板必然被拒

你的链条：

```
检测框(4 角点) → solvePnP + IPPE 双解 → 消歧 → optimize_yaw → 3D 位姿 → EKF 位置量测
```

问题：`armor_yaw` 在斜视角时病态（共面歧义），所以不得不加：

- `face_yaw_max_residual_rad = 1.05`（残差 >60° 直接拒收）
- `normal_phase_min_facing`（板不朝向相机就不用）
- `rate_max_sigma_rad_s = 6.0`（斜率太散就丢）

每一个"硬门"都在**丢观测**。丢到最后，文档实测每象限只剩 55~63°/90° 的可信弧 → ω 低估 35%（`docs/spvision25转速跟随机制报告_2026-10-25.md` §一）。

`rmcs_auto_aim_v2` 的解法不是"把门放宽"，而是**换量测空间**：直接拿灯条端点的像素做量测，斜板也还有 4 维可用。而且你**已经有这个数据**——`include/AutoAimTypes.hpp:58` 的 `std::array<cv::Point2f,4> corners` 就是它要的东西，只是在 PnP 里被丢掉了。

### 4.4 槽位重绑：状态硬改，并且协方差不动

```cpp
RotatingArmorTracker.cpp:2276   ekf_.rotatePhase(config_.pair_body_yaw_gain * dyaw);
RotatingArmorTracker.cpp:2892   ekf_.rotatePhase(delta_theta);
RotatingArmorTracker.cpp:261/2275/2895/2935/3313  ekf_.shiftCenter(...)
```

`RotatingArmorEkf.hpp:239-247`：

```cpp
void shiftCenter(const Vector3d& delta) { state_(0)+=dx; state_(2)+=dy; state_(4)+=dz; }  // P 不动
void rotatePhase(double delta) { state_(6) = wrapAngle(state_(6)+delta); }                   // P 不动
```

**状态被阶跃搬动，协方差却保持不变** → 下一帧 update 会把这个跳变当成"可信状态"，把残差重新解释掉。视觉上就是"转一下、跳一格、卡回去"。

参考实现没有这一步：`sp_vision_25` 靠 `target.cpp:138-169` 的槽位匹配把 90° 歧义吸收进**残差折叠**（`z_subtract` 对角度项做 `limit_rad`），`P` 自然变大再收敛。

### 4.5 兜底方式：硬丢 vs 降权

| | 你的项目 | 参考实现 |
|---|---|---|
| 坏观测 | 硬门拒收（`rejected_this_frame`） | R 放大，仍然 update（`target.cpp:190-196`） |
| 发散 | 各种 `relock` / `restore` / `injected_rate_until_s_` | `diverged()` 整体作废重来（`target.cpp:241`） |
| 长期偏差 | `maneuver_scale_` EMA + NIS 地板 | NIS 滑窗 100 帧，40% 失败判 lost（`tracker.cpp:84-90`） |

## 5. 为什么三天的补丁**必然**无效

把上面串起来看，你实际上在解这个方程：

```
观测覆盖 62%  →  ω 观测天然低估 35%
     ↓
想补这 35%  →  加"帧间差分"通道（tracklet / PLL / 弦长 / 切向）
     ↓
166fps 下 10 rad/s × R=0.3m 的帧间切向位移只有 2cm ≈ PnP 噪声
     ↓
差分信噪比 < 1  →  每条通道都必须加门限（否则噪到 10 rad/s）
     ↓
门限互相否决（A 通道要求 spin_streak≥8，B 通道要求 on_circle，C 通道要求 centre_still）
     ↓
同一帧里谁赢取决于门限细节  →  有时 0、有时 10、有时跳号
     ↓
再加一个通道去"修正"上一个通道  →  17 个写入点、11 个开关、354 个配置字段
```

**关键**：这条链上每一步都是"为了绕过第一步（覆盖不足）"，但没有任何一步去动**根**：

- 根 A：`Q` 太小，滤波器不相信 ω 会变 → 角度残差拉不动 ω
- 根 B：量测在 3D 位姿，斜板 yaw 病态 → 必须拒收 → 覆盖不足
- 根 C：换板用状态硬改，不用观测模型 → 每次重绑制造跳变

A 不修，就只能靠外部通道；B 不修，通道就永远缺 35% 输入；C 不修，修好了也会被跳变打断。

## 6. 改进方案（单一主线）

> 只给一条路线：**把 ω 交还给滤波器**。分 5 个阶段，每阶段有独立验收门，任一门不过就停在该阶段，不往下叠加。

### 阶段 0：先量化，不改逻辑（0.5 天）

**做什么**
1. 在俯视图 HUD 增加一行"三层相位对照"：
   - `φ_ekf = state(6)`（蓝板驱动量）
   - `φ_obs` = 本帧实测板反推的相位（绿板已有）
   - `φ_ref` = 图像域真值（用现有 `gt_omega.py` 的蓝掩模面积相位）
   - 三者两两差值 + `dφ/dt` 各自数值
2. `omega` 后面直接打印 `ω_ekf / ω_ref` 比值。

**为什么先做这个**：§1 的三个判据需要它才能读。而且它以后就是你的**验收仪**——不用再靠"看着好像不对"。

**验收门**：同一段 10 s 素材上，能稳定读出比值，且重复运行一致（±0.02）。

### 阶段 1：量测改"角度直接量测"（1~2 天）

**改什么**（最小改动、最大收益）

1. 新增量测通道 `updateFaceYawForSlot` 的模式，**默认开启**，`H` 第 4 行为 `e6`（你已有这个函数，只是默认关着）。
2. 把硬门改成 R 自适应（对齐 `target.cpp:190-196`）：
   ```
   R_angle = log(|Δangle| + 1) + 1        // Δangle = 板法向 - 中心方位（即斜视角）
   R_dist  = log(dist + 1)/200 + 9e-2
   ```
   **删除** `face_yaw_max_residual_rad` 的"拒收"语义，改为"R 放大 10 倍仍更新"。
3. 保留 NIS 拒绝（这个是对的），但阈值从 `adaptive_nis_floor=9` 改为 `chi2(4, 0.995) ≈ 14.9`，并加 100 帧滑窗（40% 失败 → lost）。

**验收门**（在 `tests/resources/rotatedifferentdirections.avi`）：
- 每象限可信弧从 55~63° 提到 **≥80°/90°**（打印覆盖率直方图）
- `ctest` 11/11 全绿
- 蓝板不再"跳格"（翻转次数 < 5/千帧）

### 阶段 2：Q/P0 提到物理量级，然后**删通道**（2~3 天）

这是核心阶段，也是唯一能根治"跟不上"的一步。

**改什么**

1. `ProcessNoiseConfig::angular_accel`：`0.01 → 10.0`
   口径：`σ_a = √10 ≈ 3.2 rad/s²`，仍保守（物理 10~15），但已是现在的 32 倍。
   > 不建议直接抄 400：那是 piecewise 口径且配 166fps 稠密角度观测。先 10，按验收门往上试。
2. `EkfInitPrior::yaw_rate_sigma_rad_s`：`3.0 → 10.0`（P0=100，对齐参考实现）。
3. **删除**下列 ω 通道（按顺序删，每删一个跑一次验收门）：

   | 删什么 | 位置 | 谁替代 |
   |---|---|---|
   | `rate_from_tracklet`（帧间差分） | `RotatingArmorTracker.cpp:2966-3081` | 角度量测 + Q |
   | `rate_from_residual`（PLL） | `:3083-3130` | 同上 |
   | `updateYawRateFromWindow`（法向斜率） | `:2031` 附近 | 同上 |
   | `injectRateObservation` + `inflateOmegaCovariance` | `:266-290`、`RotatingArmorEkf.hpp:255` | 同上 |
   | `ekf_.setRate(...)` 全部 6 处 | `:3128`、`:3232` 等 | 同上 |
   | `forced_omega_rad_s` | `:1301-1304`、`:1371` | 同上 |
   | `rate_decay_*`（ω→0 伪量测） | `RotatingArmorTracker.hpp:80-83` | 角度残差本身就会把 ω 拉回 0 |

4. 与此同时，把"静止判定"从 ω 通道移到**观测质量**上：
   - 现在：`is_static = |ω| < 1.2` 决定是否启用相位更新
   - 改成：**永远启用**相位更新，静止时角度不变，残差自然把 ω 压到 0

**验收门**：
- `rotatedifferentdirections.avi`：`|ω_ekf/ω_ref − 1| ≤ 10%`（|ω|>2 rad/s 段），方向一致
- `highspeed.avi` / `middlespeed.avi`：同上 ≤ 12%
- `stable.avi`（静止+抖动）：`|ω| < 0.4 rad/s`，不出现"自旋幻觉"（这是原来 0.01 想保的东西，删通道后靠 R 自适应保住）
- `ctest` 全绿。**如果静止场景挂了，不要退回 Q=0.01**，而是回去查阶段 1 的 R 是否真的放开了观测

### 阶段 3：槽位交给匹配器，删状态硬改（2 天）

**改什么**

1. 移植 `sp_vision_25` 的槽位匹配（`target.cpp:138-169`）：
   ```cpp
   // 对 4 个候选 slot，取 min( |fold(θ_obs − θ_model)| + |fold(β_obs − β_model)| )
   // 角度 + 方位双判据，先定 slot 再 update
   ```
2. 位置更新与相位更新**共用同一个 slot**（你已经知道这点，`updatePhaseForSlot` 的注释写得很清楚）。
3. **删除** `rotatePhase` ×3、`shiftCenter` ×6。它们的作用被"匹配器选对 slot + 残差折叠"完全覆盖。

**验收门**：
- 换板帧不再有 >30° 的相位阶跃（统计 `|φ_t − φ_{t−1}| − |ω|·dt` 的 p99）
- 蓝板与绿板相位差的中位数 < 15°、p90 < 30°

### 阶段 4：量测域迁到像素（可选，但这是"根治覆盖"的唯一解）（3~5 天）

只有阶段 0~3 之后仍觉得"斜板段跟不上"才做。

**改什么**：照 `rmcs_auto_aim_v2/robot.cpp:108-200 + 444-500` 实现：

1. 用 `ArmorDetection::corners` 算"上边中点 / 下边中点"（4 维像素量测）
2. `H = 4×11`，链式：`状态 → 4 板 8 灯条 3D 端点 → 相机 → 像素`
3. 可见性模型：夹角 <70° 双灯条、70~90° 单灯条、>90° 跳过
4. `R = 40 px²`（对角）
5. PnP 只保留给"初始化一帧"用，日常更新不再经过 PnP

**收益**：彻底删掉 `solveArmorPoseDisambiguated` 的三层消歧规则、`optimize_yaw` 的穷举、`face_yaw_max_residual_rad` 的门限——**三个补丁一起消失**。

**验收门**：覆盖率 ≥95%/90°；`ω` 误差 ≤8%；斜板段（60~85°）单独统计不退化。

## 8. 俯视图该怎么改：从"安慰画"变成"验收仪"

你现在这张图信息很全，但**有一个结构缺陷：它把"估计"和"真值"混在同一张图里，却没有给出判读规则**。

### 8.1 必须加的三样东西

1. **相位误差条**（右上角竖条）
   `Δφ = φ_obs − φ_ekf`，每帧一个点，滚动 300 帧。正常应在 ±10° 内抖动；若是单调斜线 → ω 有常值偏差；若台阶 → 槽位重绑。

2. **转速表盘**
   两个指针：`ω_ekf`（蓝）、`ω_ref`（灰，图像域谱）。下方一个大数字：**`×0.63`**（比值）。
   一眼就能读出"是慢、是跳、还是反"。

3. **视角标注**（左下角固定文字）
   `↑+x(前)  ←+y(左)  — 上帝视角，与相机视角左右镜像`
   再加一个 `--topdown-mirror` 开关（画布 x 取反），方便和视频逐帧对照。

### 8.2 必须去掉的一件事

**不要用图像域谱的结果去驱动蓝板。** 文档 §五 提到"验收口径已由 pix-rate 图像域通道满足（误差 ≤5~7%）"——那是**用真值画图**，视觉上当然好看，但它让俯视图失去了诊断价值：蓝板跟上了，你不知道是 EKF 跟上了还是谱通道在替它演。

正确做法：图像域谱只做 `ω_ref`（灰色指针、比值分母），**永远不参与状态**。

### 8.3 建议的图面分配

```
┌──────────────────────────────┬────────┐
│                              │ Δφ 条  │  ← 相位误差时序
│      俯视图（蓝=EKF 四板）    │        │
│      （绿=实测板+法向线）      │        │
│      （灰虚线=真值相位）       ├────────┤
│                              │ ω 表盘 │  ← 双指针 + 比值
│                              │ ×0.63  │
├──────────────────────────────┴────────┤
│ HUD: center / spin / obs / cov / ratio │
└───────────────────────────────────────┘
```

参考 `radar_ros_ws/src/pc_detector/src/TargetMap.cpp` 与 `src/target_matcher/include/target_matcher/visualization.hpp` 的分层画法（底图/实体/标签分离）。

## 10. 风险与开放问题

1. **Q 提到 10 之后，静止场景会不会自旋？**
   会的——如果阶段 1 的 R 自适应没做。这就是为什么阶段 1 必须在阶段 2 之前。`docs/spvision25转速跟随机制报告` §四 的"照抄陷阱"已经预警过；区别在于：**真正的护栏是 R 降权 + NIS 滑窗，不是小 Q**。
2. **`stable.avi` 的"静止不漂"断言会挡住大 Q。**
   这条断言现在保护的是"合成场景 + 硬门限"的组合。阶段 1 换成 R 自适应后，需要重新校准这条断言的容差（不是删掉，是重标）。**不要因为断言红了就退回 Q=0.01**——那是循环论证。
3. **实车安装俯仰角**（板朝外斜向上）在现有素材里是竖直的，`optimize_yaw` 的 ±15° 先验只能证明"不回归"，收益要实车验证。这条与转速问题无关，但会污染覆盖率统计。
4. **镜像站代码的可信度**：`tmp/clones/` 全部来自第三方镜像（`gh-proxy.com`），仅作阅读参考。**不要直接 `cmake` 构建或运行陌生项目的脚本**；需要编译的只有第一梯队 4 个 MIT 项目，且应在容器/独立目录里做。
5. **`tmp/clones` 体积**：当前 29 个目录、约 950 MB，其中模型/美术/视频占约 700 MB。瘦身清单见 `INDEX.md` §六（需你确认后执行）。
