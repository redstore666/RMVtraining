# 检测层诊断：与 4 个开源实现的逐项对照

日期：2026-10-25
性质：**分析与诊断，未改任何代码**。
交叉引用：EKF 侧的诊断见 `docs/转速不一致-开源对照与改进方案.md`。本篇只谈检测→位姿这一段。

---

## 0. 结论摘要

检测层有一个**确定性 bug**、两个**结构性缺陷**、一个**素材问题**。按影响排序：

| # | 问题 | 性质 | 后果 | 参考实现怎么做 |
|---|---|---|---|---|
| **D1** | 大小板用 2D 宽高比判定 | **确定性 bug** | 大板在视角 >37.5° 时判成小板 → 深度错 1.7 倍 → 位置跳 0.3~0.8 m | `type = num_id == 1 ? big : small`（编号查表） |
| **D2** | 4 角点先解 PnP 再用 3D 位姿喂 EKF | **结构性** | IPPE 双解 + yaw 病态 + optimize_yaw 穷举 + 3 道硬门，层层丢观测 | rmcs 直接拿这 4 个点当**像素量测** |
| **D3** | 置信度单级固定 0.7，无跟踪态降阈 | **结构性** | 自转目标约一半帧进不了跟踪 | 参考同样 0.7，但有 `check_type` 互校验 + 模型召回 |
| **D4** | `target_id` 作为硬标签分轨 | **结构性** | 斜板/远距离编号抖动 → 同一车分叉成多条轨迹 | 按 name 单目标跟踪 + 取最近板 |
| **D5** | v4 素材手写板尺寸与类别先验不符 | **素材问题** | 无论怎么判尺寸都错，污染三天所有实验结论 | —（需重标素材或固定尺寸） |

**最关键的一条（D2）**：你的 `ArmorDetection::corners`（TL,TR,BR,BL）与 `rmcs_auto_aim_v2` 的 `Armor2d`（tl,tr,br,bl）**逐字段同构**。rmcs 把 (tl,bl) 和 (tr,br) 当作两条灯条的 4 个端点直接喂 EKF；你把同样 4 个点送进 `solvePnP`，然后花三天修 PnP 和消歧。**检测器不用换，换消费者就行。**

## 2. D1：尺寸判定是确定性 bug（最该先修）

### 2.1 代码

`student/src/ArmorDetectorNet.cpp:84-101`

```cpp
ArmorSize classifySizeByGeometry(const std::array<cv::Point2f, 4> &c)
{
    const double outer_w = (cv::norm(c[0]-c[1]) + cv::norm(c[3]-c[2])) / 2.0;  // 上下边
    const double h_avg   = (cv::norm(c[0]-c[3]) + cv::norm(c[1]-c[2])) / 2.0;  // 左右边
    const double ratio = outer_w / h_avg;
    return std::fabs(ratio - 4.04) < std::fabs(ratio - 2.37) ? Large : Small;   // 判决点在 3.2
}
```

### 2.2 为什么斜视角必错

板面与视线夹角 θ 时，宽度被压缩、高度基本不变：

```
ratio_obs ≈ ratio_true · cos θ
```

- 小板：2.37 · cosθ 恒 ≤ 2.37 → 永远判 small（不会错）
- 大板：4.035 · cosθ
  - 判 large 需要 `4.035·cosθ > 3.2` → **θ < 37.5°**
  - **θ > 37.5° 就判成 small**

而一块板从"正对"到"完全侧转"要走 90°，其中 **37.5°~70°（约 32° 弧）必然误判**。自转车每块板每圈都会经过这段。

> 注：这是几何近似（忽略俯仰和透视非线性），但量级和边界是对的。严格值可用 `cv::projectPoints` 对 230×57 的板在 θ∈[0,80°] 扫描验证，10 行代码。

### 2.3 级联后果（这是重点）

判错尺寸 → `buildObjectPoints` 给出错的物点 → PnP 求出错的深度：

```
d = f · (W/2) / (w_px/2)     →     d ∝ W
W: 0.230 (大板) vs 0.135 (小板) →  比值 0.587
```

**深度直接错 41%**（估近了）。若真实距离 1.0 m，位置观测会跳 0.41 m；若 2.0 m 则跳 0.83 m。

这与既有文档里那句数字对得上：

> "id=3 观测相邻帧位移中位 0.063 m、**p90 0.412 m**：每 4 帧一次 0.4 m 级跳变"
> —— `docs/孪生消歧与转速跟进分析_2026-10-25.md` §2.1

**"观测源跳变"很可能不是检测在跳板，而是同一块板的尺寸判定在帧间翻转。** 判据很简单：把 `ratio` 和 `size` 打出来，看 0.4 m 跳变的那几帧 `size` 是否正好翻转。

第二条级联：物点错 → 重投影误差变大 → 撞上 `kMaxReprojErrorPx=6.0` 被**拒收**：

```
板投影宽 ~150 px，物点宽错 41% → 残差约 150×0.41/4 ≈ 15 px > 6 px
```

**误判的帧不是"差一点"，是"直接被丢"** —— 覆盖率就是这么掉下去的。

### 2.4 参考实现怎么做的

`sp_vision_25/tasks/auto_aim/armor.cpp:179`（YOLOv5 构造）：

```cpp
type = num_id == 1 ? ArmorType::big : ArmorType::small;
```

**编号查表，一条线。** 不测量几何、不看宽高比。理由是：编号分类（9 类，同一台车跨帧稳定）比尺寸回归（随视角连续变化）可靠得多。

而且它还有一道互校验（`yolov5.cpp:206-213`）：

```cpp
bool check_type(const Armor& armor) const {
  auto name_ok = (armor.type == ArmorType::small)
      ? (armor.name != one && armor.name != base)                        // 小板 ≠ 英雄/基地
      : (armor.name != two && armor.name != sentry && armor.name != outpost); // 大板 ≠ 2/哨兵/前哨
  ...
}
```

**"尺寸 vs 编号"互相验证，矛盾就丢。** 你的代码没有这一步。

你的 `decodeYolo11` 分支是对的（`det.size = prop.large ? Large : Small`，来自 38 类），但**默认跑的是 YOLOv5 分支**。

### 2.5 修复

```cpp
// 二选一，都只要几行
// 方案 A（对齐参考）：编号查表
det.size = (det.target_id == 1) ? ArmorSize::Large : ArmorSize::Small;

// 方案 B（更稳）：几何判 + 编号互校验，矛盾时以编号为准并降权
```

修完必须重新跑那三天的 A/B —— 因为**之前的对比基线本身就带着这个 bug**，结论可能是反的。

## 3. D2：你的输出和 rmcs 一模一样，只是消费者不同

### 3.1 逐字段对照

| 你的 `ArmorDetection`（`AutoAimTypes.hpp:55-62`） | rmcs `Armor2d`（`src/utility/robot/armor.hpp:37-57`） |
|---|---|
| `corners[0..3]` = TL, TR, BR, BL | `tl, tr, br, bl` |
| `color` | `color` |
| `target_id` | —（有 `genre`/`shape`） |
| `size` | `shape` |
| `confidence` | `confidence` |

**完全同构。** 连角点顺序都一致。

rmcs 怎么用（`robot.cpp:525-560`）：

```cpp
observable.upper2d[left_id]  ← armor.tl     // 左灯条上端
observable.lower2d[left_id]  ← armor.bl     // 左灯条下端
observable.upper2d[right_id] ← armor.tr     // 右灯条上端
observable.lower2d[right_id] ← armor.br     // 右灯条下端
// 量测 = 一条灯条的上下端点 = 4 维像素
```

也就是说，`corners` 的 TL/BL 就是左灯条两端，TR/BR 就是右灯条两端。**你手上一直有 rmcs 需要的全部数据。**

### 3.2 PnP 这一段到底付出了什么代价

| 代价 | 你的现状 |
|---|---|
| IPPE 双解歧义 | `solvePoseForTrack` 里三套选解规则（误差差 >3px / 深度先验 / 上倾先验 `:722`） |
| yaw 病态 | `optimizeArmorYaw` ±70° 穷举（`:814-960`） |
| 深度对尺寸敏感 | D1 的级联 |
| 3 道硬门 | `:1130-1152`，误判直接丢 |
| 斜板被丢 | 覆盖率 55~63°/90°（既有文档实测） |

而 rmcs 的同一段：

```cpp
// robot.cpp:444  直接对像素做 EKF 更新，H 是 4×11
innovation = { upper.x - pred_upper.x, ... , lower.y - pred_lower.y };
// 可见性: <70° 双灯条全用；70~90° 只用朝相机那条；>90° 跳过
```

**没有 PnP、没有双解、没有 yaw 穷举、没有尺寸敏感、没有硬门。** 斜板不是"被拒收"，而是"少用一半信息"。

### 3.3 这意味着什么

- 你不需要换模型、不需要重训、不需要新检测器。
- 需要的是：**在 `armor_solve` 之外，开一条"像素直通"通道**，把 `corners` 直接送进 EKF（或先送进一个轻量的角度量测）。
- PnP 只保留给"首帧初始化"用一次。

这条就是 EKF 报告里的阶段 4，但由于检测层同构，它的**成本比报告里估的低**——不需要新数据源，只是复用已有字段。

## 4. D3：置信度单级固定 0.7

`student/src/StudentTasks.cpp:328`

```cpp
static float g_nn_min_confidence = 0.7F;
```

`ArmorDetectorNet.hpp:69-70` 的注释自承：

> "复检/跟踪阶段可以降到 0.3~0.5 换取召回（**自转目标实拍只有约一半的帧能过 0.7**）"

但 `setArmorScoreThreshold` 只被两个测试调用（`test_camera_playback.cpp:955`、`test_camera_system.cpp:433`），**生产路径从不降阈**。

对比：

| | 阈值 | 是否有二次机会 |
|---|---|---|
| 你的项目 | 0.7 固定 | 无 |
| sp_vision_25 | 0.7 预筛 + 0.8 终筛（更严！） | 模型是关键点回归，斜板召回好；`check_type` 只剔矛盾样本 |
| rmcs | yaml 可配 | 可见性模型决定用不用，不看置信度硬门 |

**注意别照抄"降阈值"这个思路**：参考实现阈值比你还高。它靠的是"模型召回 + 不轻易丢观测"。降阈值只会引入更多误检，让 D1/D4 更严重。

正确的顺序是：先修 D1（别丢对的）、再谈召回。

## 5. D4：`target_id` 当硬标签

`tests/test_camera_playback.cpp:1500+` 和 `MultiTargetTracker` 都按 `target_id` 分簇、分轨。

问题：`target_id` 是模型 9 类编号的 argmax。斜板、远距离、部分遮挡时，编号分数接近，argmax 会抖。一旦抖：

- 同一台车的相邻帧被分到不同 `target_id`
- 多目标器建立两条轨迹，各拿一半观测
- 每条轨迹的 ω 都只有一半的更新率 → 更跟不上

既有文档里那句"场景里有多个 3 号板，检测在它们之间跳"就是这一层。

参考做法（`sp_vision_25/tracker.cpp:270-290`）：

```cpp
// 按 name + armor_type 匹配到唯一 target_，再在候选里取 min_x（最靠前的板）
for (auto& armor : armors) {
  if (armor.name != target_.name || armor.type != target_.armor_type) continue;
  ...
}
```

**编号只用来"选目标",不用来"分轨迹"**；轨迹由几何邻近（上一帧位置）维持。

建议：编号降级为软标签；分簇用 3D 邻近（你 `drawDetectedBody` 里已经有聚类代码，`TopDownView.cpp:581-611`，直接复用）。

## 6. D5：素材问题（会让前三天结论全部失效）

`StudentTasks.cpp:626-635`

```cpp
// 诊断开关：板上实际尺寸未知时，用环境变量扫一遍尺寸对 PnP 深度的影响
// （v4 的手写"3"板明显比 135mm 大，框宽中位 156px 对应 ~0.25m）
if (const char *ow = std::getenv("ARMOR_HALF_W")) half_w = std::atof(ow);
```

**v4 素材的板约 250 mm，而类别先验（num=3）对应 135 mm。** 差 1.85 倍。

后果：

1. 不管 D1 判 large 还是 small，只要不是 250 mm，深度就是错的；
2. 深度错 → 位置错 → EKF 的 `center` 和 `r` 都错；
3. `optimize_yaw` 的 ±70° 穷举在错的平移上做，最优点也会偏。

**这是元问题**：三天的 A/B 实验，基线本身可能就不自洽。建议：

- 短期：把 `ARMOR_HALF_W=0.125`（250mm 的一半）固定进实验脚本，让深度先对；
- 中期：换标准尺寸素材（`tests/resources/*.avi` 是合成的，尺寸可控），或重新标注实测板尺寸。

## 7. 修复顺序（与 EKF 报告阶段对齐）

| 序 | 动作 | 对应 EKF 阶段 | 成本 | 验收判据 |
|---|---|---|---|---|
| 1 | **修 D1**：尺寸改编号查表 + 加 `check_type` 互校验 | 阶段 0 之前 | 半天 | 同一 `target_id` 的 `size` 帧间翻转率 < 1%；p90 位移从 0.412 m 降到 < 0.15 m |
| 2 | **固定 D5**：实验脚本锁定真实板宽 | 阶段 0 | 10 分钟 | 深度中位数与卷尺/真值差 < 5% |
| 3 | **加诊断**：打印 `ratio`/`size`/`reproj`/`box_w` | 阶段 0 | 半天 | 能一眼看出 0.4 m 跳变对应哪一帧、哪个字段翻 |
| 4 | 加编号↔几何一致性过滤（D4 软化） | 阶段 3 | 1 天 | 同一台车的轨迹数 = 1 |
| 5 | 像素直通通道（D2） | 阶段 4 | 3~5 天 | 覆盖率 ≥95%/90°；不再需要 IPPE 消歧 |

**不要跳序。** 第 1 步很可能直接把"转速跟不上"改善一大截——因为 EKF 这边一直在追一个每 4 帧跳 0.4 m 的观测源。

## 9. 一句话总结

检测层的问题不是"检测不准"，而是**检测出来的东西被误读了两道**：

1. 尺寸被几何关系误读（D1）→ 物点错 → 深度错 → 观测跳变 → 被门拒收；
2. 位置被 PnP 误读（D2）→ 4 个本来干净的像素点，被压成一个病态的 3D 位姿，再花三套规则去修它。

**四个角点本身是好的。** rmcs 证明了这个数据结构足够支撑到 ω 收敛；你只是多了一道 PnP 和一套消歧，而它们在斜视角下会把好数据变成坏数据。
