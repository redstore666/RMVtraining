## 零、先纠正我上一版报告的一个错误结论

上一版报告说"1.csv 半径从 0.207 单调漂到 0.226 且不可逆 → 代码 bug"。

用毫秒时间戳重新切分后，真相是：

| 文件 | 时长 | 帧率 | 半径起点 | 半径终点 | 半径全程 min~max |
|---|---|---|---|---|---|
| 1.csv | 62.3 s | 80 Hz | **0.2005** | 0.2230 | 0.2005 ~ 0.2261 |
| 2.csv | 63.5 s | 79 Hz | 0.2854 | 0.2854 | **0.2854 ~ 0.2854（全程零变化）** |
| 3.csv | 63.5 s | 79 Hz | 0.2854 | 0.2854 | **0.2854 ~ 0.2854（全程零变化）** |

**1.csv 的真实形状不是"漂移"，是分三段、每段内部完全冻结：**

```
t =  0.0 ~ 24.9 s   R = 0.2066 ~ 0.2070    ← 冻结（|w| ≈ 0.05~0.18，静止/平移）
t = 24.9 ~ 31.1 s   R = 0.2074 → 0.2166    ← 解锁爬升（|w| ≈ 0.9~1.1）
t = 31.1 ~ 34.3 s   R = 0.2166 → 0.2236    ← 继续爬（|w| ≈ 0.15~0.67）
t = 34.3 ~ 37.4 s   R = 0.2241 → 0.2261    ← 到位
t = 37.4 ~ 62.3 s   R = 0.2261 → 0.2230    ← 再次冻结
```

也就是说：`radius_frozen_` 闸门在正常工作（该冻的时候冻住了），
**问题是它在 0.207 就冻死了，而真值是 0.28 —— 冻结在错误的值上，且 3.csv 静止 63 秒也没能把它掰回来。**

这个结论比"漂移"严重得多，因为它直接说明：**我们的半径第一次锁定定错之后，没有任何机制能把它纠正到真值。** 下面第五节展开。

## 一、架构骨架对比：我们其实和同学 2 同源，差异是"加了什么"而不是"换了什么"

| 维度 | 我们 | RMVtraining1（同学 2） | rm_autoaim-hxr（同学 hxr） |

| EKF 状态维数 | **11** | 13 | 独立 ArmorEkf 模块 |
| 状态量 | cx,vx,cy,vy,z,vz,yaw,ω,**R, radius_diff, height_diff** | cx,vx,cz,vz,y0,y1,·,**R**,·,yaw,ω,y2,y3 | — |
| 半径来源 | **6 条写入路径**（5 条已关死，1 条活）+ 冻结闸门 | **1 条**：(f) 段滑动窗 RMS 软观测 | 常量钉死 r=0.303 + clamp |

**结论先说：骨架（EKF 状态含中心+R+yaw+ω 的笛卡尔/CTRV 混合模型）我们和同学 2 是一样的，不存在"架构选错"的问题。**

真正的差别是三条，而且全部是**"我们多做了什么"**：

1. **我们多了 radius_diff / height_diff 两个状态（11 vs 13 维中额外的两个刚体参数）** —— 这是借鉴 sp_vision_25 的 l/h，用于表达"前后对板比左右对板离车心远"。方向是对的，但它让半径的可观测性变得更差（见第三节）。
2. **我们在半径上建了 6 条写入路径 + 冻结闸门** —— 同学 2 只有 1 条软观测，**不冻结**。这是最关键的行为差异。
3. **我们的观测噪声只有重投影自适应，没有深度自适应** —— 同学 2 有 `(z/z_ref)²`。这一条能解释 2.csv 旋转段"EKF 距离系统性偏大 6.12 cm"。

## 二、差异 1（最关键）：半径是"冻结"还是"持续软观测"

### 2.1 两种策略

**我们的（freeze_radius=true，默认）：**
```
锁定那一刻用三点圆拟合 / 双板弦长算出 R
→ applySlowRadius() 低通逼近候选值
→ 残差 < 1% × R 连续 5 次 → radius_frozen_ = true
→ 之后 applySlowRadius() 第 1967 行直接 return，永不更新
```

**同学 2 的（每帧都在做）：**
```
每个 (f) 段都跑一次：
  |ω| > 1.5 rad/s 且中心速度 < 0.5 m/s（原地旋转）
    → 取最近 166 帧（≈1s，覆盖整圈）板位置的 RMS 离质心距离
    → RMS ≈ 真实半径（整圈几何恒等式）
    → 用 σ=0.02 m 的软观测喂给 EKF，每帧更新
  否则（静止/平移）
    → 用 σ=0.06 m 的弱先验锚回 0.20，只防塌缩、不硬锁
```

### 2.2 为什么这条差异直接造成我们实测的失败

| 我们的现象 | 冻结策略下的解释 |
|---|---|
| 1.csv 静止 25 s，R 冻在 0.2066 | 锁定那次圆拟合给了 ~0.207，进入冻结闸门后再无写入口 |
| 1.csv 3.csv 静止 63 s，R 冻在 0.2854 | 锁定那次给对了，运气好 |
| 3.csv 全程 R 一位不变 | 冻结态的正常表现（不是 bug，是设计） |
| **1.csv 的 R 从头到尾没到过 0.28** | 冻结闸门把错误答案固定住了 |

**关键是：我们的冻结判据判的是"低通值追上了候选值"，而不是"候选值是错的"。**
`radius_freeze_residual_ratio = 0.01`，残差 < 1% 就锁。只要候选值自己稳定（哪怕是 0.207 这个错值），5 次之后就锁死。
从代码注释也能看出设计者知道这个问题（"实测锁在 0.207/0.240"），但当时的解法是继续调冻结参数，而不是加一条"事后纠错"的通道。

### 2.3 只调参能救吗？

**不能完全救，但能大幅改善，且有一个 3 行的最小代码开关可以救。**

- 调参侧：`radius_prior_small_m` 目前是 0.20、`radius_prior_large_m` 是 0.25。你的道具真值是 0.28 —— **两个先验都比真值小**。
  如果这是自制道具（我上一版报告里也提到"实拍 v4 的自制道具半径 0.28"），那么**按板型选先验这条路本身就带着错误的先验**。
  1.csv 锁在 0.2066，恰好就是"小装甲板 0.20 先验 + 一点数据修正"的结果 —— 起点错，冻结就冻在错处。
- 但这只是"把答案告诉滤波器"。真正的架构缺陷（锁错了无法纠正）还在。

**最小代码改动（明天的保险，不是必须）：**
在 `applySlowRadius()` 的冻结分支（第 1967 行 `if (radius_frozen_) return;`）前面加一个"解冻条件"：
连续 N 秒（比如 3 s）检测到 `|EKF R - 弦长分位半径| > 15% × R` 就 `radius_frozen_ = false`。
好消息：已核实 `noteChordRadius()` 在 `step()` 第 3537 行**无条件调用**，不经过 `applySlowRadius` 的冻结闸门，
所以冻结之后 `chord_radius_samples_` 仍在持续填充 —— **纠错所需的证据本来就是齐全的，只是没人去读它。**
**这条改动 ~10 行，不动任何状态维数、不动 EKF 数学、不动观测模型，风险可控。但建议验收后再做。**

### 2.4 建议

| 时机 | 动作 |
|---|---|
| **明天验收前（今天）** | 上车命令加 `--radius 0.28`（或者改 `radius_prior_small_m/large_m = 0.28`）。**这是零风险的调参，必须做。** |
| 验收后 | 把冻结改成"软冻结"：冻结只降 `applySlowRadius` 的 alpha 到很小（比如 0.01），不彻底 return。一行改动，保留稳定性又留纠错通道。 |
| 长期 | 移植同学 2 的 (f) 段思路：旋转时用整圈 RMS 回归半径。这是唯一有几何保证的半径来源。 |

## 三、差异 2：观测噪声只看重投影、不看深度

### 3.1 对比

**我们（`RotatingArmorTracker.cpp:317`）：**
```cpp
const double scale = std::clamp(0.5 + reproj_error / position_sigma_quality_gain,  // gain=2.0
                                position_sigma_quality_floor, 3.0);
observation.sigma_position_m = position_sigma_m * scale;   // position_sigma_m = 0.03
```
→ σ 只在 **0.03×floor ~ 0.09** 之间变化，**与距离无关**。

**同学 2（`kReprojNoiseGain = 0.15, kRefDepthM = 2.0`）：**
```
σ² ∝ (1 + 0.15·reproj²) × (z/2.0)²
```
→ 4 m 处 (z/2)²=4，σ 自动放大 2 倍；2 px 干净观测时 1+0.15×4=1.6。
**好坏观测的动态范围是 6.4× × 16× ≈ 100×，我们只有 3×。**

### 3.2 这条能解释什么

2.csv 旋转段 **EKF 距离系统性偏大 +6.12 cm（std 10.91 cm、p95 25.75 cm，10 个时间块 9 个为正）**。

单板 PnP 的深度误差 σ_z ∝ z²/f，距离越远、深度越不可信。我们给所有距离同一个 σ，
结果就是：**中远距离的脏观测和近距离的干净观测被赋予同样权重**，滤波器的深度估计被系统性拉偏。
兄弟工程用 (z/z_ref)² 正好把这件事按物理规律建模了。

### 3.3 只调参能救吗？

**部分能，但会牵一发。**

- 把 `position_sigma_m` 从 0.03 提到 0.045~0.05：整体降权，距离偏差会小，但**静止精度也会变差**（现在静止 PnP 0.57px、位置抖差 0.7 mm，是很好的成绩，别丢了）。
- 真正的解法是加上 `(z/z_ref)²` 因子。代码上就是 `RotatingArmorTracker.cpp:317` 那个 `scale` 多乘一项 —— **3 行，纯观测噪声建模，不动状态维数、不动关联、不动冻结逻辑**。这是所有架构差异里**改动面最小、收益最直接**的一条。

**我的建议：这条可以考虑今天做（如果你还有时间），因为它是纯加法，回放能验证。**

## 四、差异 3：11 维多了 radius_diff / height_diff

我们的状态：
```
[cx, vx, cy, vy, z, vz, yaw, ω, R, radius_diff, height_diff]
```
同学 2 是 13 维但**没有** radius_diff/height_diff（它是 yaw 的多分支 y0..y3，解决的是相位分支歧义，不是半径非对称）。

sp_vision_25 的 l/h 是合理的物理建模：真实四板不共圆。但代价是：

**R 和 radius_diff 在观测上强耦合。** 单板观测只给出"圆心在板心 + R·n 这条射线上"，
多了一个 radius_diff，就等于多了一个可以"吸收"残差的自由度 —— 这正是 1.csv 里 R 从 0.2066 爬到 0.2260 的机制之一：
不是数据把 R 推上去，而是滤波器拿 R 去换残差。

**但这条不建议动。** 理由：
1. 删掉两个状态要改 `kStateDim`（11→9）、改雅可比、改 Q 对角、改所有测试断言 —— 这是**架构改动**，明天验收前绝对不做。
2. 有 `freeze_radius` 闸门 + 正确的 `--radius 0.28` 先验之后，这个耦合的破坏力被压制住了。

**持有，记为已知架构债。**

## 七、专项：既然是打道具，"区分多车"逻辑是不是会误判？

用户点名这个问题。追到底的结论是：**逻辑确实存在，而且默认开着，但在当前"单道具单板号"场景下一次都进不去；风险是潜伏的，不是已发生的。**

### 7.1 三条路径的实际情况

| 路径 | 位置 | 是否接入生产 | 默认 | 当前能否触发 |
|---|---|---|---|---|
| `MultiTargetTracker` 多目标粘合层 | student/src/MultiTargetTracker.cpp（370 行） | **否**。只在 `test_camera_playback.cpp:960`、`test_multi_target.cpp` 构造 | — | **否（不在链路上）** |
| `target_switch_enabled` | RotatingArmorTracker.cpp:3482 | 是 | **true** | **否** |
| `prefer_centered_target` | RotatingArmorTracker.cpp:3427 | 是 | **true** | **否** |

生产链路证据：`StudentTasks.cpp:1225-1227` 只有一个 `static RotatingArmorTracker instance`；
`main.cpp`（724 行）与 `StudentTasks.cpp` 全文均无 `MultiTarget` 引用。

### 7.2 为什么进不去：`target_id` 是板号不是车号

```cpp
// ArmorDetectorNet.cpp:55-57
// 映射到工程 target_id：sentry->7, one..five->1..5, outpost->6, base->8, 8->0(丢弃)
constexpr int kYolov5NumToTargetId[9] = {7, 1, 2, 3, 4, 5, 6, 8, 0};
```

`target_id` = **装甲板上印的数字**（1~8），不是车辆身份。道具板上是 3，于是全场板号恒为 3：

- `frame_id`（:3412-3420，本帧出现最多的板号）恒 = 3 = `target_id_`
  → `frame_id != target_id_` 永不成立 → `target_switch` 分支永不进入
- `prefer_centered_target`（:3427-3459）要求存在 `observation.target_id != target_id_` 才能算出 `other_best`
  → `std::isfinite(other_best)` 恒 false → 永不进入

### 7.3 实测数据印证

| 文件 | `target_id` 分布 | `detection_id` 分布 | `target_switch` |
|---|---|---|---|
| 1.csv | 3 × 5000 | 3 × 5000 | 0 次 |
| 2.csv | 3 × 5000 | 3 × 4997 + **5 × 3** | 0 次（id=5 误检被 `other_id_streak` 门槛拒绝，占 0.06%） |
| 3.csv | 3 × 5000 | 3 × 5000 | 0 次 |

1.csv 丢板段（`target_found=0`，共 105 帧 / 2.1%）：
`t=12.15~12.72s`、`t=44.37~44.62s`、`t=53.72~54.05s` —— 均未触发换目标。

**所以"误判"不能归因于多车逻辑。** 已知的三个真问题（半径冻结、距离偏差、丢板）都不在这条线上。

### 7.4 但它是潜伏炸弹

只要画面里同时出现两种板号（旁边有真车进场），这两条默认分支立刻开始工作，
而它们**换的是"板号"不是"车"**——那一刻就会串车。

### 7.5 建议：验收前不改，验收后用开关关掉

**验收前不改**的理由：当前场景下这两条分支一次都进不去（5000 帧数据佐证），改它收益为 0；
而 `prefer_centered_target` 的注释（hpp:450-455）明确记录过"迟滞 0.10 让目标每 270 帧翻一次、
EKF 从没稳定过"的实测翻车，动它有风险。

**验收后的最小改动（2 行，零行为变化）：**
```cpp
// RotatingArmorTracker.hpp:334
bool target_switch_enabled{false};
// RotatingArmorTracker.hpp:457
bool prefer_centered_target{false};
```
关掉后 `other_id_streak_` 恒 0、`centered_streak_` 恒 0，代码走原路——
**单目标场景本来就不触发，所以这不改变任何已验证行为**，比删代码安全。

`MultiTargetTracker.cpp` + `test_multi_target` 未进生产链，验收后连同 5 条死半径路径一起清。

## 九、今天的操作清单（按优先级，全部零风险）

### 必须做

1. **改常量，把半径先验设成 0.28** —— ⚠️ 注意：`--radius` **只在测试程序里实现**（`tests/test_camera_playback.cpp:267`），
   **上车主程序 `main.cpp` 根本没有这个参数**（我第一版写错了，已核实 `main.cpp` 全文无 radius 解析）。
   所以今天的做法只能是改常量：

   `student/include/RotatingArmorTracker.hpp:125-129`
   ```cpp
   double radius_prior_m{0.28};        // 0.25 → 0.28
   double radius_prior_small_m{0.28};  // 0.20 → 0.28
   double radius_prior_large_m{0.28};  // 0.25 → 0.28
   ```
