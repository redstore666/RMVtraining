# 答辩提纲

现场验收按评分表列的八个必验场景走。本文按顺序给出每个场景的演示命令、看什么、
预期结果，然后是可能被追问的问题和答法。

演示前先确认三件事：串口设备权限（`ls -l /dev/ttyACM*`，需要 `dialout` 组）、
相机被别的进程占用（`fuser /dev/video*`）、`config/camera.yaml` 里的 `calibrated`
标志与实际外参状态一致。

---

## 一、必验场景

### 1. 空目录构建

```bash
cd /tmp && rm -rf rmv_build && cmake -S <工程目录> -B rmv_build -DCMAKE_BUILD_TYPE=Release
cmake --build rmv_build -j$(nproc)
```

要说明的是为什么强调"空目录"：开发期间一直在已有的 `build/` 上增量编译，
曾有两次改动没被重新编译（一次是 CMake 里的 OpenVINO 查找，一次是改了头文件里的
默认参数但没触发重编），车上跑的还是旧二进制，排查了很久。现在每次出包前都在
干净目录完整编一遍。

如果 OpenVINO 装在 venv 里，需要加 `-DOpenVINO_DIR=...`。CMakeLists 里写了自动
搜索，但装在非标准路径时仍可能找不到，这时会明确报 `Could not find OpenVINO`。

### 2. 串口收发

没有实车时用虚拟串口：

```bash
./tools/virtual_serial.sh --status 5 --hz 60        # 一个终端，模拟电控
./build/rmv_training /tmp/ttyVMS 115200 config/camera.yaml 8080
```

`--status 5` 表示敌方蓝方，`--hz` 是发帧频率。脚本按 64 字节协议逐字段填充，
帧布局和 `通信结构体.md` 对拍过。

验收时看：

- 读线程有没有正确收满 64 字节（日志里打印帧头帧尾检查结果）；
- `crc` 字段的变化是否跟着 EKF 状态走（无目标 0、稳定 1、有目标未稳定 2），
  在 Web 页面上就是 `ekf_state` 那条曲线的值；
- 写出去的帧里 `center_x/center_y` 是毫米、`distance` 是分米还是米——这一处按
  `通信结构体.md` 的原始定义来，不能自己改单位。

**要强调的是 `crc` 不是校验和。** 结构体里它叫 `crc` 但语义是 EKF 状态机，
任务书第 3.2 节明确要求不实现校验算法。这是最容易扣分的地方，被问到要能立刻说清。

### 3. 相机取流与断流处理

```bash
./build/test_camera_live --red
```

正常取流时状态栏显示 `fps_cam`（相机固件报的帧率）和 `fps_nodisp`（实际处理帧率），
两者差值是处理耗时占用。当前实测 1440×1080 下约 30 fps 取流、实际处理 25 帧左右。

演示断流：直接拔相机网线。预期表现是 `get_pic` 超时返回 false，连续 3 次后操作
线程报错退出循环但进程不崩，Web 服务还活着；插回网线后 `MV_CC_StartGrabbing`
重新初始化成功，取流自动恢复。

如果现场不方便拔线，可以说清楚代码里这条路径怎么走的，并指出
`release_camera()` 的调用时机。

### 4. 静态装甲板识别与 PnP

```bash
./build/test_solve tests/data/synth_large_5.png --red
```

输出四个角点、`ArmorSize`、`target_id`、置信度、距离、yaw/pitch、重投影误差。

现场摆真板时用 `test_camera_live`，在画面上直接看角点标注。要能说明：小板
135×57 mm、大板 230×57 mm，物点建表时除 1000 转米；`SOLVEPNP_IPPE` 是平面目标
专用解法；重投影误差 >6 px 拒绝的阈值来自误差分布（正常 P95 约 4 px，坏批次
中位 8 px）。

### 5. 平移、旋转与换板

```bash
./build/test_camera_playback tests/resources/redrotate.avi --red --ekf --topdown
./build/test_camera_playback tests/resources/bluemove.avi  --blue --ekf --topdown
```

`--topdown` 打开右下角俯视图。这是答辩时最有说服力的一块：灰线是模型认为的四块板、
绿线是 PnP 直接看到的板、红点是车心、橙箭头是速度、绿点是瞄准点。转起来以后灰线
和绿线是否贴合，一眼就能判断转速跟不跟得上。

平移场景看车心红点是否按真实轨迹走（相机固定在画布左边缘，走 2 m 就往右挪
226 px），速度箭头方向与实际运动方向一致。旋转场景看四块板是否整体随 yaw 转而不是
一格一格跳。

换板：观察瞄准点是否在板之间平滑过渡，以及切换时有没有短暂的无目标（这是安全
设计，切到新编号时要先输出 NoTarget）。

**注意 redrotate 必须用 `--red`。** 用 `--blue` 会检出 0 个，这个坑踩过一次。

### 6. 遮挡与重新出现

用手或纸板遮住目标 0.2~0.3 s：

| 阶段 | 预期 |
| --- | --- |
| 遮挡瞬间 | 状态从 Stable 降到 Unstable（`crc=2`），立即禁开火 |
| 持续遮挡 | 保持纯预测，不更新，状态值仍然有限（不出现 NaN） |
| 遮挡 >0.6 s | 清空为 NoTarget（`crc=0`），`target_id` 归零 |
| 恢复 | 重新锁定，10 帧内回到 Stable |

要能解释 0.6 s 这个阈值：纯外推 0.3 s 时板位置误差 0.0198 m，0.6 s 涨到 0.09 m
量级，再往后就超过板宽了，继续外推没有意义。

### 7. Web Debug

```bash
# 打开 http://127.0.0.1:8080
```

任务书 3.7 要求的四类量都在：

- 帧率与处理耗时：`grab_ms`、`detect_ms`、`solve_ms`、`total_ms`
- 检测数量、编号、置信度：`detect_count`、`target_id`、`confidence`
- PnP 距离、yaw/pitch、重投影：`distance_m`、`target_yaw`、`target_pitch`、`reproj_err_px`
- EKF 车心、速度、yaw、角速度、半径、状态：`ekf_cx/cy`、`ekf_vx/vy`、`ekf_yaw`、
  `ekf_omega`、`ekf_radius_1_m`、`ekf_state`

刷新页面的同时观察相机画面是否卡顿。不卡是因为 Web 服务在独立线程、日志走加锁的
环形缓冲，操作线程只做 put 不做网络 IO。

可以补充一点：这些日志同时是离线分析的数据源，`webdebugs/` 下的 CSV 就是历次
实车导出的，实验报告第 7.9 节的四场景命中率就是从这些 CSV 和回放算出来的。

### 8. 正常退出

```bash
# Ctrl-C
```

预期：读线程先停、再停操作线程（停流并释放相机）、最后停 Web 服务。进程退出码 0，
不出现 "device busy"、"double free" 之类的告警。重新启动能立刻拿到设备，说明
`MV_CC_CloseDevice` 和 `DestroyHandle` 都走到了。

## 二、可能被追问的问题

**Q：为什么用神经网络而不是传统视觉？**

两种都实现过。传统视觉（HSV + 灯条配对 + 数字分类）在实拍上能跑，但维护成本高：
环境光变化要重调 HSV 区间，实拍里出现的"共享灯条假板"、"掩码被上帧残留污染"、
"孪生板翻号"三个问题每个都要加特判。关键点模型直接回归四角点，这三类错误消失。
代价是需要 OpenVINO 运行时，以及模型文件要随作业提交。取证图在 `tests/evidence/`。

**Q：`crc` 字段是什么？**

EKF 状态机，不是校验和。0 = 无目标，1 = 预测稳定，2 = 有目标但未稳定。任务书
3.2 节明确要求不实现 CRC 算法。开火许可只可能在 `crc=1` 时给出。

**Q：状态为什么是 11 维？**

前九维覆盖任务书 3.6 节要求的全部量：中心平移（cx/vx/cy/vy）、车体 yaw 与角速度、
装甲板高度（z/vz）、旋转半径。后两维 `radius_diff`、`height_diff` 描述四板车的
**非对称刚体参数**——前后一对板比左右一对离车心更远、也常高一点，偶数槽位用
`radius`、奇数槽位用 `radius + radius_diff`。它们默认开启，但只在同帧双板可见
时才有信息（单板帧对应雅可比列为零），所以滤波器自己决定跟不跟。

**Q：半径是怎么来的？**

三处先验统一 0.28（`radius_prior_m` / `_small` / `_large`），锁定那一刻用圆拟合或
弦长解给出实测值，与先验差超过容差就退回先验。容差是
`min(0.35 × 先验, 0.08 m)`——原来只有等比项，先验从 0.20 调到 0.28 后容差跟着
变宽，放行了 0.3673 的歪解（真值 0.28，偏 31%），锁定即歪。加了 0.08 的绝对上限
之后命中率从 26.1% 回到 32.2%。

半径在锁定后冻结，只有重锁时才可能更新。这是高速单板场景误差偏大的直接原因：
视场内只有一块板时，"半径"和"车心位置"在几何上不可分辨，只能靠先验。

**Q：为什么 sinspeed 只有 32.2%，redrotate 有 67.0%？**

转速几乎一样（4.90 vs 4.69 rad/s），差别在可见板数。sinspeed 素材里同帧出现两块板
的帧只占 0.6%，等于全程单板观测。单板只能给一个板心，相位不可观测，切向误差被
放大到 p50 9.94 cm；redrotate 有相当比例的双板帧，切向 p50 降到 3.72 cm。

所以这不是调参能解决的。做过外推补角扫描（scale 从 0 到 1.5 共 7 档），1.0 已在
极值，再加大反而变差，说明瓶颈是切向误差带宽而不是提前量不够。要往上走得改观测
配置（比如把车身相位模 π/2 升为主观测，或者用 LED 灯条做互补量测）。

**Q：开火判据为什么不用角度误差？**

旧判据是角度误差 ≤0.05 rad，看着很严。但角度要乘距离才是实际脱靶量：1.5 m 处
0.05 rad 就是 7.5 cm，比小板半宽 6.75 cm 还大，竖直方向是板半高 2.85 cm 的 2.6 倍。
角度"对上了"照样打飞。

现在换算成板面内的脱靶量：`distance·tan(yaw_err) ≤ 0.6·half_w`，竖直同理。
0.6 是给弹道散布和延迟抖动留 40% 余量。

**Q：外参标定了吗？**

内参标了（21 张棋盘格，重投影 0.07 px）。外参目前是拆分状态：平移
`t = [0.06711, 0, 0.05150] m` 是车上量出来的实值，旋转仍是占位，实际用的是固定的
轴重排（相机 右/下/前 → 云台 前/左/上）。

这个状态暴露过一个 bug：原来的判据是"R≈I 且 |t| 很小"才算未标定，于是"R 占位、
t 是真值"被判成已标定，90° 重排被跳过，而回放侧又强制施加这层旋转并把 t 清零，
两条路走的不是同一条。现在拆成 `rotationIsPlaceholder()` 和 `hasTranslation()`
两个独立判据，`test_ekf_pipeline` 有一条单测钉住。

影响：跟踪的相对几何（中心、半径、角速度、换板）是自洽的，绝对瞄准角有安装倾斜
带来的系统偏差。标定方法写在 `云台外参.md`，手眼标定 `AX=XB`，棋盘固定、云台取
10~15 组姿态。没做的原因是实车只有两次上电机会，都用在链路联调上了。

**Q：为什么初始化要先声明转不转？**

3 维观测估 11 维状态，单帧自由度足够拟合得很好，所以拟合残差不能用来判断收敛。
合成实验里，单帧板残差只有 4~8 mm 时车体中心误差仍可能到 0.43 m——观测被"相位在转"
解释成"中心偏了一点加半径偏了一点"。`yaw_rate=0` 冷启动在 8 个噪声种子上只有 5 个
能锁对。

反过来也不行：对静止目标，"yaw 缓慢漂移 + 中心同步平移"是模型的近零空间方向，
板位几乎不变，数据里学不出"它没转"。

所以声明是必须的，而且要能被观测反驳。`declarationContradicted` 比较板面法向斜率
和 EKF 的 `yaw_rate`，连续 6 帧偏差 >1 rad/s 就重锁。

**Q：声明错了会怎样？**

两种失败方式不一样，这一点比较关键：

- Static 声明用在旋转目标上：0.3 s 纯外推板误差从 0.0198 m 涨到 0.1479 m，是
  响亮失败，会被自检发现并重锁；
- Spinning 声明用在静止目标上：外推误差只有 0.0234 m，看起来正常，但状态完全错
  （dyaw 2.73 rad，dω 0.57 rad/s）。静默失败。

所以静止目标需要"数据先声明、观测再反驳"的双向机制，不能只靠外推误差发现。

**Q：双线程怎么防数据竞争？**

读线程只做读帧和写入 `latest_gimbal_`，操作线程进来先复制一份然后完全不碰共享区，
之后取流、检测、预测都不需要锁。共享变量用一个 mutex 保护，读线程不做任何计算，
操作线程不持锁做耗时操作。最坏情况读线程等一次拷贝的时间。

**Q：车体 yaw 有 2π/N 模糊怎么办？**

这是模型固有的对称性，不是估计误差。四块板几何完全相同时，把 yaw 平移 90° 后板位
集合不变，任何只看板位置的观测都无法区分。不影响瞄准（瞄准点是具体的板）和角速度，
但状态里的 yaw 绝对值只能在模 90° 意义下确定。测试断言都按模 2π/N 写。

**Q：相机断流怎么处理？**

`MV_CC_GetImageBuffer` 超时 500 ms 返回失败 → `StopGrabbing` 后重新 `StartGrabbing`，
最多重试 3 次。仍失败则释放句柄返回 false，上层连续 3 次空帧后退出操作线程。
进程不崩，Web 服务继续跑。

**Q：为什么空帧还要继续走检测和 PnP？**

任务书第 4 节要求。目的是让 EKF 有机会做纯预测——如果空帧直接跳过后面的环节，
短时遮挡时会丢失预测连续性。连续空帧超过 3 次才退出，最终输出仍然强制为无目标。

**Q：听说之前有 3 项 ctest 是失败的？**

是的，现在 12 项全过。那 3 项里，`ekf_model_convergence` 和 `ekf_init_contract`
是测试夹具的问题：状态从 9 维加到 11 维后，`tests/ekf_test_support.hpp` 的
`truthState()` 仍只用 9 个系数初始化 `Matrix<double,11,1>`，Eigen 的逗号初始化器
断言崩溃——修夹具后两项通过。`ekf_tracker` 的 G 组卡在 8 rad/s 的"瞄准点落在
朝相机那一面"断言上（当时 90%，另两档 100%/98%/100%），补 11 维夹具后同一断言
通过，属于边界现象而非回归。

关键点：修的是夹具，没有放宽断言、也没有跳过用例。这三项在加 11 维状态之前
就已经失败，用 `git stash` 回到基线对拍确认过。

## 三、演示顺序建议

时间有限时按这个顺序，前四项能覆盖约 50 分且最不容易出问题：

1. 空目录构建（证明工程完整）
2. 静态板识别 + PnP（最稳，数据漂亮）
3. 平移回放 + 俯视图（99.8% 命中率，直观）
4. 遮挡演示（状态机逻辑清楚）
5. 串口联调（需要设备，风险高）
6. 旋转回放（67%，切向误差要能解释）
7. 高速单板（32.2%，主动说明瓶颈和已定位的原因，比被问出来好）
