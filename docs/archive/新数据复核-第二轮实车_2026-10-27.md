## 一、半径：0.28 没有到达车上

### 1.1 数据事实

| 文件 | R 起点 | R 终点 | 全程范围 | 首次变化时刻 |
|---|---|---|---|---|
| sin.csv | **0.20000** | 0.20426 | [0.20000, 0.20426] | t = 24.66 s |
| combine.csv | **0.29034** | 0.29027 | [0.28807, 0.29127] | t = 47.51 s |

- `0.20000` 精确等于 `radius_prior_small_m = 0.20` 的默认值 —— 这是"先验原样输出"，不是量测。
- `0.29034` 不等于 0.28，它是锁定时刻圆拟合/弦长解出来的实测值。
- **两者都不是 0.28，说明车上跑的二进制用的还是旧先验。**

### 1.2 源码现状

```
student/include/RotatingArmorTracker.hpp:125   double radius_prior_m{0.25};
student/include/RotatingArmorTracker.hpp:128   double radius_prior_small_m{0.20};
student/include/RotatingArmorTracker.hpp:129   double radius_prior_large_m{0.25};
```

全仓 grep `0.28`，只命中**历史注释**（例如 "实拍 v4 的 3 号道具半径 0.28"），**没有任何一处赋值**。

### 1.3 最可能的三个原因

1. **改了源码但没重新编译**，或编的不是同一个 `build/` 目录（车上跑的还是旧二进制）。
2. **只改了 `radius_prior_m`（0.25），没改 `radius_prior_small_m`（0.20）**。
   `radius_prior_from_size = true`（默认），代码走的是 small/large 分支（`RotatingArmorTracker.cpp:993-1000`），
   `radius_prior_m` 根本不参与 —— 这就是 sin.csv 输出精确 0.20000 的原因。
3. 改完了但没重启进程（长驻程序不会热加载常量）。

### 1.4 顺带发现的一条硬证据：冻结是真的"一次性"

sin.csv 里把两个时刻对齐看：

```
半径首次变化  t = 24.66 s   0.20000 -> 0.20392
板号切回 3    t = 24.66 s   id 2 -> 3
```

**完全同一帧。** 说明：
- 半径在 t=0~24.66 这 24.7 秒里一位没动（`radius_frozen_ = true`）；
- 直到发生**重新锁定**（换目标导致 reset），冻结状态被清掉，半径才开始动。

这印证上一份报告的核心判断：**半径只在锁定那一刻决定，之后永不自纠**。上一轮 1.csv 锁死在 0.207 是同一个机制。

### 1.5 该怎么改（今天）

改**三处**，缺一不可：

```cpp
// student/include/RotatingArmorTracker.hpp:125-129
double radius_prior_m{0.28};        // 0.25 → 0.28（兜底）
double radius_prior_small_m{0.28};  // 0.20 → 0.28（关键！sin.csv 走的就是这条）
double radius_prior_large_m{0.28};  // 0.25 → 0.28
```

改完**必须**：
```bash
cd <车上工程目录>
rm -rf build && cmake -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j4
```
（或者至少 `cmake --build build -j4`，但要确认编的是你跑的那个 build 目录）

**验证方法**（跑 30 秒就够）：看导出的 CSV 里 `ekf_radius_1_m` 第一帧是不是 0.28。
如果是 0.20 或 0.29，说明还是旧二进制。

## 二、距离偏差：上次的 +6.12 cm 已经消失

### 2.1 复核口径

和上一轮一致：EKF 距离（`topdown_distance_m`）减 PnP 距离（`pnp_distance_m`），
按**毫秒时间戳 ±25 ms 最近邻对齐**（不能用行号对齐，两者写入时刻不同）。
本轮额外做了两项过滤：
- 只保留 `pnp_distance_m` 在 0.3~8 m 的合理帧；
- 只保留 `target_found > 0` 的跟踪中帧（外推期 EKF 会跑远，混进来会污染统计）。

### 2.2 结果

| 文件 | 对齐帧 | 中位 | 均值 | p95 | 偏大比例 |
|---|---|---|---|---|---|
| sin.csv | 3613 | **+0.02 cm** | −0.98 cm | +11.52 cm | 50.7% |
| combine.csv | 2813 | **+1.91 cm** | +1.95 cm | +14.04 cm | 62.6% |

按转速分档：

| 文件 | 静止 \|ω\|<1 | 中速 1~3 | 高速 \|ω\|>3 |
|---|---|---|---|
| sin.csv | −0.62 cm | +0.12 cm | **−0.04 cm** |
| combine.csv | +0.23 cm | +3.22 cm | **+5.12 cm** |

### 2.3 判断

- **sin.csv 的旋转段偏差归零**（+0.12 / −0.04 cm）。上一轮 2.csv 旋转段那种 +6.12 cm 的**系统性**偏大不再出现。
- combine.csv 残留 +5 cm 集中在高速段。但这份数据是"移动/旋转不断切换"，
  EKF 每换一次运动模式都要重新收敛，**瞬态滞后**会造成几百毫秒的偏差，
  这是"频繁切换"的固有代价，不是系统性缺陷（偏大比例 62.6% 也印证只是轻微单向偏）。
- **结论：不需要再动 `position_sigma_m` 或加深度自适应。** 上一轮我建议的 `(z/zref)²` 改动暂不必做。

## 三、串车这次真的发生了（推翻上一轮"进不去"的结论）

### 3.1 事实

上一轮三份 CSV 里 `target_id` 全程恒为 3，我判断两条换目标分支"一次都进不去"。
**这次不成立了。**

`sin.csv`：

| 时间 | 事件 |
|---|---|
| t = 5.57 ~ 7.84 s | 检测出其他板号：2 号 131 帧、1 号 13 帧、4 号 4 帧、7 号 1 帧（共 149 帧，占 2.5%） |
| **t = 8.82 s** | **锁定板号 3 → 2**（串车） |
| t = 8.82 ~ 24.66 s | **锁在 2 号板上 15.8 秒** |
| t = 24.66 s | 切回 3 号板（同时触发半径重置，见 §1.4） |

`combine.csv` 只有 2 帧 id=2 误检，没有造成串车。

### 3.2 机理

`target_switch_enabled`（默认 true）的判据是：
"锁定板号连续 2 帧消失，且本帧有别的板号" → `dropTarget("target_switch")`。

t=5.6~7.8 s 那 2.3 秒里数字识别抖动，2 号板号占了上风 → 连续 2 帧满足 → 换目标。
这和"有没有真车"无关，**是数字识别噪声在投票**。

### 3.3 这就是我上一轮说的"潜伏炸弹"炸了

上一轮的结论要修正为：

> 那两条分支在当前场景下**不是进不去**，而是**需要数字识别抖动来触发**。
> 一旦识别器把道具板号认成别的数字，换目标逻辑就会工作——它换的是"板号"，不是"车"。

### 3.4 处置建议（今天可做，风险低）

鉴于已经实测到 15.8 秒串车（这比任何理论风险都硬），**这两条开关建议今天就关**：

```cpp
// student/include/RotatingArmorTracker.hpp:334
bool target_switch_enabled{false};   // true → false
// student/include/RotatingArmorTracker.hpp:457
bool prefer_centered_target{false};  // true → false
```

**为什么这次风险比上次评估的低**：
- 单目标场景下这两条本就不该工作，关掉后 `other_id_streak_` 恒 0、`centered_streak_` 恒 0，
  走的是原路径，**不改变任何已验证的单目标行为**；
- 反过来，开着它们的实测代价是 15.8 秒跟错板 —— 比"理论上有风险"更明确。

> 注意：`target_switch_enabled=false` 后，如果真丢目标，靠 `timeout_s` 超时重置 + 重新 Collecting 恢复，
> 这是原有的主路径，不受影响。

## 六、半径调大后的回归：容差是"等比"的，先验越大越宽松

### 6.1 现象

把半径先验 0.20 → 0.28 之后，`sinspeed.avi` 回放的命中率从 **32.4% 掉到 26.1%**。
第一反应是"是不是 `prefer_centered_target` 的影响"，于是做了 A/B：

| 变量 | 命中率 |
|---|---|
| `prefer_centered_target=true` | 26.1% |
| `prefer_centered_target=false` | 26.1%（**完全相同**） |

再单独隔离半径：

| 半径先验 | 命中率 |
|---|---|
| 0.20 | 32.4% |
| 0.28 | 26.1% |

结论：与换目标逻辑无关，**纯粹是半径先验调大引起的**。这很反直觉——先验从 0.20 改到正确的 0.28，
按理应该更准，结果反而更差。

### 6.2 根因

锁定日志打出了真正的凶手：

```
[EKF] 帧 31 阶段 collecting -> tracking（样本 30，半径 估 0.367303，omega 5.66174
      误差 0.165304，来源 法向序列，圆R 0.225518 残差 0.054838 有效步 0）
末帧状态: ... omega=2.30473 R=0.367303
```

锁定时半径被估成 **0.3673**（真值 0.28，偏 **31%**），连带 omega 从 5.66 被拽到 2.30。
第一帧就锁歪，后面 `applySlowRadius()` 又被限速（`radius_max_step_m=0.0005`）和冻结双重锁死，再也拉不回来。

为什么先验调大反而放行了这个歪解？因为容差公式是**等比**的：

```cpp
const double data_radius_tolerance = 0.35 * size_prior;   // 旧
```

用 Python 验算三条先验下的接受区间：

```
先验=0.20  容差=±0.070  接受区间=[0.130, 0.270]   0.3673 被接受? False
先验=0.25  容差=±0.087  接受区间=[0.163, 0.338]   0.3673 被接受? False
先验=0.28  容差=±0.098  接受区间=[0.182, 0.378]   0.3673 被接受? True   ← 放行
```

`0.35 × 0.28 = 0.098`，上界正好爬到 0.378，把 0.3673 这个 31% 歪的解放了进来。
**先验调大 → 容差跟着膨胀 → 更歪的解放行**，这是个真实的架构缺陷，不是调参失误。

### 6.3 修复

容差加绝对上限，等比项只用来照顾"先验本身就不准"的场合：

```cpp
// student/src/RotatingArmorTracker.cpp
const double data_radius_tolerance =
    std::min(0.35 * size_prior, config_.data_radius_tolerance_max_m);
```

```cpp
// student/include/RotatingArmorTracker.hpp
double data_radius_tolerance_max_m{0.08};
```

`0.08` 的取法：真值 0.28 时接受区间收紧到 `[0.20, 0.36]`，能容忍圆拟合的常见偏差，
但挡得住 31% 这种量级的歪解。改完 `sinspeed` 锁定半径回到 **0.28（先验）**，命中率回到 **32.2%**。

## 七、开火基线（验收对照）

- 全部用 `test_camera_playback <avi> --ekf --headless --topdown` 跑，`--red`/`--blue` 按视频颜色。
- **Stable 帧数**：`crc`（EKF 状态）== 1 的帧数，对应通信结构体里的"稳定可开火"。
- **命中率**：`test_camera_playback` 自带的"到期对准"评估——取瞄准时刻之后 ±10ms 平滑观测参照，
  判断切向 + 竖直脱靶量是否落在板面内且板朝相机。这是**离线回放口径**，不是实车打靶成绩。

### 7.2 sinspeed 按角速度分档（高速是难点）

| \|omega\| 档 | 样本 | 命中率 | 切向 p50 / p90 |
|---|---|---|---|

### 7.3 偏移扫描说明了什么

`sinspeed` 的偏移扫描（`|omega| 1-5` 档）：

```
-120:21% -100:32% -80:43% -60:48% -40:42% -20:31% +0:24%
+20:17% +40:13% +60:10% +80:8% +100:7% ...
```

命中率峰值出现在 **−60 ~ −80**，按老解读会得"系统整体偏提前、应回收 prediction_latency"。
**这个解读 2026-10-27 被 7.6 的扫参推翻了**：把外推补角比例从 1.0 降到 0.6 时，
峰值立刻从 +0 挪到 −40、再降到 0.3 时挪到 −60。也就是说"峰值在负偏移"本身
可以由"外推补得不够"造成，**不能反推当前补多了**。而在 scale=1.0 时峰值就在 +0，
说明当前外推量正好——**不要再往回收**，回收只会掉命中率（0.6 → 30.5%，0.3 → 16.1%）。

`sinspeed` 32% 的上限来自切向误差带宽（p90 30 cm vs 板半宽 6.75 cm），
不是提前量，也不是 ω 估计偏小。

### 7.5 更正：正弦场景**不存在**反向旋转（用户 2026-10-27 质疑）

我之前口头说过"正弦场景 ω 从 +7.87 在 −2.01 之间来回翻转"，**这句话是错的**，
把极值当常态了。重新核 `webdebugs/sintestnew.csv`（5000 帧 / 53.3 s）：

| 判据 | 数值 |
|---|---|
| ω > +0.3 rad/s | 3837 帧 = **76.7%** |
| ω < −0.3 rad/s | 44 帧 = **0.88%**，分布在 12 个连续段，最长 0.11 s |
| \|ω\| ≤ 0.3（死区） | 1119 帧 = 22.4% |
| 分位 | p1 −0.24 / p5 −0.02 / p50 **+2.00** / p95 +4.16 / max +7.87 |
| 负段时刻 | 7.36 / 13.11 / 15.31 / 19.01~19.26 / **21.52~21.63（谷值 −2.015）** / 39.64 s |

**运动学上不存在反向旋转**：−2.015 出现在 21.5 s 的 0.11 s 窗口里，前后 ω 都是 +0.65~+0.85。
它是一段瞬态毛刺，不是"转到另一侧去了"。

#### 毛刺的归因（已定位到代码）

开启 `TRACK_DEBUG=1` 抓 `[ev]` 证据行，1624 帧里有 **55 帧（3.4%）** 的 used 斜率 < −0.3，特征完全一致：

```
yaw=+4.84 bear=-2.25 used=-2.25 src=bear
```

即 **同帧 yaw 斜率仍是 +4.84，只有方位角(bearing)斜率翻成负的**，而整合逻辑是
"分歧时取弦向/采信的那一路"，于是负值被原样送进 EKF，把 ω 从 +0.85 拽到 −2.015。

根因在弦向证据的**折叠周期**：`fold(Δdir, π)` 在配对时距对应的 |ω·Δt| 落到
(π/2, π) 区间时，折叠会给出**反号**的斜率。这个负号是折叠的副产品，不是物理量。

#### 已修（本轮唯一代码改动）

`student/src/RotatingArmorTracker.cpp` 第 3c' 段（弦向整合）：

- 同号 → 照旧逆方差加权；
- **异号 → 只吸收幅度**（取两者 |·| 均值），符号沿用已接受那一路，sigma 放大到两者较大者。

验证：

| 项目 | 改前 | 改后 |
|---|---|---|
| `[ev]` 中 used<−0.3 的帧 | 55 / 1624 (3.4%) | **55 / 1624 (3.4%) 不变** |
| sinspeed 命中率 | 659/2046 = 32.2% | **32.2%（逐帧完全一致）** |
| bluemove / redrotate / nearmove | — | 未变 |

> **重要**：这次改动在现有四段回放上**没有任何数值变化**——因为
> `sinspeed.avi` / `bluemove.avi` 这些录像是"车与相机相对静止"的转台/推车素材，
> 双板帧只有 0.6%，`chord_samples_` 几乎攒不起来，弦向分支根本不触发。
> 改动是**针对实车 sin 场景**（`sintestnew` 那份数据是车辆真实正弦摆动，
> 双板帧多得多）的定向修复，回放验证不到，只能在车上验。


### 7.6 外推补角比例扫描（关键负结果）

给观测外推加了一个临时缩放 `angle = scale · ω · horizon`，扫 sinspeed：

| scale | 命中率 | >5 rad/s 档偏移扫描峰值位置 |
|---|---|---|
| 0.0 | 3.9% | −80 ms / 75% |
| 0.3 | 16.1% | −60 ms / 64% |
| 0.6 | 30.5% | −40 ms / 40% |
| 0.8 | 32.9% | — |
| **1.0（当前）** | **32.2%** | **+0 ms / 26%** |
| 1.2 | 28.2% | +20 ms / 20% |
| 1.5 | 23.5% | +20 ms / 16% |

**结论：1.0 已经落在极值上，外推量是对的，不要再调。**
scale 越小，峰值越往负偏移跑（补得越少、越需要靠延迟去凑），这是"欠补"的典型形状；
反过来 scale>1 命中率单调下降。所以 sinspeed 32% 的上限**不是外推补少了**，
而是切向 p90 仍有 30 cm（板半宽 6.75 cm）——误差带宽的问题，不是提前量的问题。

诊断参数已回退，`aim_extrapolate_scale` 不在成品里。
