## 2. 一个必须先对齐的事实：俯视图显示的是哪条 ω

- 俯视图 HUD 的 `spin omega` 取的是 **`state(7)`**（`src/TopDownView.cpp:1029`），即**纯 EKF 的 ω**。
- 存档明确记录：**纯 EKF 的 ω 至今 ≈0**，卡点是**观测覆盖**（检测只出正对板框），"不是估计器也不是圆拟合"（§十七、孪生消歧 §2.2）。
- 能跟到 7~8.5 rad/s 的那条 ω 是**面积谱 / pix-rate 通道**（§十八~二十五：FFT 梯式精修 + Ceres 正弦拟合，A=0.65 b=7.84 Ω=2.12），**不是 EKF**。

而当前三个相位类开关**全是默认关**（`RotatingArmorTracker.hpp:268 / 305 / 357`）：

```cpp
bool phase_update_enabled{false};
bool pair_phase_update_enabled{false};
bool slot_phase_update_enabled{false};
```

→ EKF 的 ω 目前**只由位置量测驱动**。位置观测有 41.6% 的槽位翻转 + 0.4 m 级跳变，
ω 学不上去是结构性的，与"关联公式写得好不好"关系不大。

## 3. 因此方案要改

原方案"角度门控 + 双帧一致 + 每板每帧至多一次"——**角度部分删掉**（已否决两次），保留后两条。

新方案（顺序）：

1. **先确认用户看的是哪条 ω**（HUD 的 state(7) 还是 pix-rate 的显示）——
   这决定了要不要动 EKF，还是只需把两条通道对齐显示。
2. 若确认要看 EKF 的 ω：**先做观测覆盖**（§十七钉死的真根因），
   再做**解析可见性模型**（唯一未做过、且正好治"两块板同时可见"）。
3. 单板路径、联合绑定、Q 参数：**一律不动**。
